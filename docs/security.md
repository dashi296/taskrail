# 安全性

taskrail は、リポジトリへの書き込み権限と API キーを持つエージェントを自動で動かします。
前提は「エージェントは指示を忘れることがあり、入力には悪意が混ざりうる」です。
指示に頼らず、構造で守ります。

## 脅威と対策

| 脅威 | 対策 | 実装 |
| --- | --- | --- |
| Issue 本文やコメントに埋め込まれた指示(プロンプトインジェクション) | 入力をタグで囲み、データとして扱うよう指示する。タグを閉じる文字列は無害化する | `core/prompt.ts` |
| 〃 によって AI が「合格」と報告する | 自己申告を信用せず、根拠(受け入れ条件、指摘)との矛盾を検査する | `core/result.ts` |
| 〃 によって AI が列を動かす・マージする | AI は Issue にもラベルにも触れない。列を動かすのは `apply` だけ。マージ権限は誰にも与えない | `commands/apply.ts`、ブランチ保護 |
| 権限のない人がラベルを変えて AI を起動する | ラベルを動かした人の write 権限を確認する | `commands/route.ts` |
| 承認を飛ばす遷移(inbox → ready など) | 遷移を主体ごとに定義し、許可されていない遷移では起動しない | `core/flow.ts` |
| Issue コメントに偽の仕様・実行記録を書き込む | マーカーは信頼する投稿者(Actions では App、ローカル実行では gh のログインユーザー)のコメントからだけ読む | `core/record.ts`、`core/context.ts` |
| エージェントの出力(要約・質問・指摘など)に偽のマーカーを仕込み、実行記録や仕様を偽造する | 実行記録のマーカーはコメントの先頭だけを読む。成果物は最後のマーカーだけを読む。エージェント由来の文字列はすべて無害化する | `core/record.ts` |
| エージェントが書き込み用の認証情報で、Issue やラベルに直接書き込む・push する | エージェントには読み取り専用の App トークンを渡し、checkout にトークンを残さない(claude-code-action はこのトークンを origin の URL に埋め込むため、エージェントからは読めるが、読み取り専用である)。apply は origin を使わず、URL を直接指定して push する。ローカル実行では gh と git の認証を外して起動する | ワークフロー、`scripts/local-run.sh` |
| エージェントが `.git` の hook や設定、`origin/*` の ref を書き換えて、apply の検査を欺く | apply の git 操作では hook と fsmonitor を無効にする。比較の基準は API で取得した SHA。git の失敗は違反として扱う。push 先を書き換える設定(`url.*.insteadOf` / `url.*.pushInsteadOf` / `remote.origin.pushurl`)がリポジトリにあれば push しない | `core/git.ts`、`commands/apply.ts` |
| 読み取り専用の工程でコミットを作る・ほかのファイルを書く | 書き込めるのは結果ファイルの置き場所だけで、Bash は渡さない(`git diff --output=` などで任意の場所に書けるため)。差分は route が書き出す。リモートにないコミットも違反として検出する | `commands/route.ts`、`commands/apply.ts` |
| 権限のない人の修正依頼で列を戻し、その文面を実装エージェントに渡す | 修正依頼を出した人の write 権限を確認する。実装に渡すレビューは write 以上の人のものだけ | `commands/board.ts`、`adapters/github.ts` |
| AI が CI 定義や設定を書き換える | `protected_paths` の変更を検出したら push せずに止める | `commands/apply.ts` |
| AI がルール文書、エージェントの設定(`.claude/`、`.mcp.json`)、CI の定義を書き換え、後続の工程や CI で実行させる | これらは設定では外せない保護パスにする。名前の変更・削除も検出する。シンボリックリンクの追加・変更・削除は保護対象への変更とみなし、既存のリンクのリンク先の変更はリンクの名前でも照合する | `core/config.ts`、`core/git.ts` |
| CI が複数あるとき、一部の成功だけで検証へ進む | 実装の記録のコミットで、検査がすべて成功し、監視している CI(PR で動いた実行)がすべて成功してから進める。問い合わせ中に push されたら進めない。その列に入った後の実装の記録がなければ(差し戻しや修正依頼の直後)進めない | `commands/board.ts` |
| fork の同名ブランチの PR で列が動く | 同じリポジトリのブランチだけを対象にする | ワークフロー |
| 読み取り専用の工程で AI がコードを変更する | 作業ツリーに変更があれば違反として止める。差分を読む工程では、検証したコミットがブランチの先頭と一致することも確かめる(書き込み直前にもう一度確認する) | `commands/apply.ts` |
| blocked の質問に、権限のない人が答えて指示を注入する | 回答として渡すのは write 以上の人のコメントだけ。直近の記録が blocked のときに限る。プロンプトでは未信頼の入力として扱う | `core/answers.ts`、`flow/prompts/_common.md` |
| ローカルの検査(`--local-checks`)が、エージェントの書いたコードを手元の認証情報つきで実行する | 記録した sha だけを取り出した作業ツリーで、認証情報になりうる環境変数を落とし、HOME を使い捨ての場所に向け、gh・git・ssh の設定を読ませない。sandbox ではないので、任意のコードが利用者の権限で動くことは変わらない | `core/checks.ts` |
| エージェントの実行中に人間が列を戻す・Issue を閉じる | apply は、Issue が open で、列が実行時と同じで、blocked でないときだけ結果を反映する(開始時と書き込みの直前に確認) | `commands/apply.ts` |
| 実装と検証の無限ループ、コストの暴走 | 差し戻しの上限、`--max-turns`、ジョブのタイムアウト、WIP 上限 | `core/flow.ts`、ワークフロー |
| 配布元の改ざん | 導入先は taskrail をタグで参照する。実行時に外部の URL から指示を取得しない | `templates/` |
| 異常時に止められない | リポジトリ変数 `TASKRAIL_ENABLED=false` で全ジョブが即終了する(apply を含む。値はジョブの開始時のもの) | 全コマンド |

## 導入時に必ず行うこと

1. **既定ブランチを保護する。** レビュー必須(承認1件以上)、直接 push 禁止。App にバイパス権限を与えない。
   `taskrail doctor` が、承認数とバイパスの設定まで確認します。
2. **記録を信頼する投稿者を確認する。** Issue コメント内の記録(実行記録・仕様・計画)は、信頼する投稿者のものだけを読みます。
   Actions では GitHub App のログイン名(`bot_logins`。`TASKRAIL_BOT_LOGIN` で自動設定)、
   ローカル実行(`scripts/local-run.sh`)では gh のログインユーザー(`TASKRAIL_RECORD_AUTHOR`)です。
   どちらもなければ、どの記録も信頼しません。
3. **CODEOWNERS を設定する。** `.github/`、`taskrail.yml`、マイグレーション、認証まわりは人間のレビューを必須にする。
4. **設定の変更権限を確認する。** 設定をリポジトリ変数 `TASKRAIL_CONFIG` に置くと、`protected_paths` や `bot_logins` を
   PR レビューなしで変更できます。変数を変更できる人を限定するか、`taskrail.yml`(CODEOWNERS の対象)に置いてください。
5. **Secrets を最小限にする。** taskrail のジョブに、本番環境やクライアントの認証情報を渡さない。
6. **public リポジトリでは特に注意する。** 外部の人が Issue を書けます。
   `ai::ok` は write 権限のある人が付ける運用にし、自動で付く設定を見直してください
   (トリアージエージェントの提案は、ラベルが未設定のときだけ採用されます)。

## 残っているリスク

- **apply はエージェントと同じ job で動きます。** GitHub がホストするランナーでは、エージェントは Bash と sudo を使えるため、
  後から動く apply の実行環境(taskrail の実行ファイル、PATH など)を書き換えられます。
  この場合、書き込み用トークンを持つ apply を完全には守れません。apply を別の job に分ける対策を検討しています(taskrail の Issue #18)。
  それまでは、外部の人が書き込める Issue では `ai::ok` を付ける人を限定してください。
- **ローカル実行(`scripts/local-run.sh`)は、エージェントを手元の端末で動かします。** gh と git の認証は外して起動しますが、
  エージェントは `~/.ssh` などのファイルを読めます。信頼できる Issue だけに使ってください。

- **書き込み工程のエージェントは Bash を使えます。** テストや lint を実行するために必要ですが、
  ランナー上の環境変数やネットワークにアクセスできます。`claude-code-action` は一定の対策をしていますが、
  完全ではありません。機密性の高いリポジトリでは、ネットワークを制限したセルフホストランナーの利用を検討してください。
- **App トークンは Organization のインストール範囲で発行しています**(taskrail リポジトリの取得のため)。
  App のインストール先を、taskrail を使うリポジトリに限定してください。
- **`pass` の内容的な正しさは保証しません。** 矛盾は検出しますが、検証エージェントが誤って合格にすることはあります。
  最後の防壁は人間のレビューです。Human Review を省略しないでください。
- **トリアージの `ai::ok` 提案**は、Issue 本文に影響されます。認証や課金に触れる Issue が `ai::ok` になっていないか、
  仕様の承認時に確認してください。

## 問題を見つけたら

`TASKRAIL_ENABLED` を `false` にしてから、taskrail リポジトリの Issue で報告してください。
