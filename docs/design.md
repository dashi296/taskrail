# 設計

## 位置づけ

taskrail は開発手法ではなく、既存の手法を自動で回すためのワークフロー・フレームワークです。
考え方は借り物で、独自なのは「それをボードとラベルと CI で実際に回る形にしたこと」です。

| 借りている考え方 | taskrail での形 |
| --- | --- |
| 仕様駆動開発(Spec → Plan → Tasks → Implement) | Spec 列と Plan 列を分け、それぞれ人間が承認する |
| Stage-Gate | 列の間にゲートを置き、条件を満たさなければ進めない |
| Evaluator-Optimizer | 実装エージェントと検証エージェントを別コンテキストにし、往復に上限を設ける |
| Safe Outputs(GitHub Agentic Workflows) | エージェントは結果を書くだけ。書き込みは検証後に別の処理が行う |
| Harness Engineering | ルールは文書より linter・テスト・CI で強制する。短い地図 + 構造化された docs |

## 1回の実行

```
ラベル変更 ─▶ route ─▶ エージェント ─▶ apply ─▶ ラベル変更 ─▶ …
             決定的      AI            決定的
```

**route**(決定的)
1. キルスイッチ、Issue の状態、`blocked`、`ai::ok` を確認する。
2. ラベルを動かした人に write 権限があるか、その遷移がその主体に許可されているかを確認する。
3. Issue コメントから最新の仕様・計画・差し戻しの指摘を取り出す(信頼するのは `bot_logins` のコメントだけ)。
4. 工程に必要な文脈だけでプロンプトを組み立て、`.taskrail/run/` に書き出す。
5. 作業ブランチを用意する(実装・検証の工程)。

**エージェント**(AI)
プロンプトファイルを読み、作業し、結果を JSON で書き出す。Issue にもラベルにも触れない。

**apply**(決定的)
1. 結果ファイルをスキーマで検証する。ファイルがない、形式が不正、別のエージェントを名乗る結果は不備として扱う。
2. 自己申告と根拠の矛盾を検査する(満たしていない受け入れ条件がある `pass`、`major` の指摘がある `pass` など)。
3. 強制ルールを検査する(読み取り専用工程での変更、保護パスの変更、未コミットの変更、コミットのない `pass`)。
4. `decide()` が次の列を決める。ここがフロー上の唯一の判断箇所。
5. コメント → 補助ラベル → 列の移動、の順に書き込む。列の移動が次のイベントを発火させる。

## 状態の持ち方

状態はすべて Issue にあります。エージェントやランナーには何も残しません。

| 情報 | 場所 |
| --- | --- |
| 現在の列 | `flow::` ラベル(1つだけ) |
| 停止中か | `blocked` ラベル |
| 仕様・計画 | taskrail のコメント内、`<!-- taskrail:artifact spec -->` 以降 |
| 実行の記録 | taskrail のコメント内、`<!-- taskrail:run {...} -->`(工程、結果、遷移先、taskrail の版) |
| 差し戻しの回数 | 実行の記録から数える。spec / plan に戻るとリセット |
| 作業中のコード | ブランチ `issue-<番号>-<slug>` と PR |

このため、途中で落ちても同じラベルを付け直せばその工程からやり直せます。
また、どの版のプロンプトで作られた成果かを後から追えます。

## コンテキストを小さく保つ

- 1工程1セッション。前工程の会話履歴は引き継がず、成果物(仕様・計画・差分)だけを渡す。
- 工程ごとに渡す文脈を `src/core/prompt.ts` の `NEEDS` で決める。
  コードレビューには仕様を渡さず、実装には Issue の議論スレッドを渡さない。
- Issue の長い議論は、仕様化エージェントが確定事項を仕様にまとめ直す。以降の工程は仕様だけを読む。
- 1 Issue = 1 PR = 半日以内。ターン数が上限に近づく Issue は「分割が足りない」というシグナル。

## 遷移の権限

`flow.yml` は、誰がどの遷移を行えるかを3種類に分けて定義します。

| 主体 | 定義 | 例 |
| --- | --- | --- |
| agent | `on_result`、`auto_approve` | inbox → spec、verify → review、verify → doing |
| human | `human_next` | spec → plan、plan → ready、review → done |
| system | `system_next` | ready → doing(dispatch)、doing → verify(CI成功)、review → done(マージ) |

仕様の承認(spec → plan)と計画の承認(plan → ready)は human にしか許可されていません。
許可されていない遷移を検出すると、route はエージェントを起動せず、`blocked` にして理由をコメントします。

## CLI を薄く保つ

フローの定義は `flow/` のデータで、CLI はそれを読んで実行するだけです。
CLI の中で LLM を呼ぶことはしません。テストしにくく、壊れやすくなるためです。
判断が必要な導入作業(ルール文書をリポジトリ向けに書く)は `plugin/` の skill が担当し、skill から CLI を呼びます。

## 拡張するとき

- **列やエージェントを増やす**: `flow/flow.yml` に stage を足し、`flow/prompts/<agent>.md` を置く。
  渡す文脈を絞るなら `NEEDS` に追加する。`npm run check` が整合性を検査する。
- **プラットフォームを増やす**: `src/adapters/types.ts` の `Platform` を実装する。`core/` は変更不要。
- **強制ルールを増やす**: `src/commands/apply.ts` の「強制ルール」に足す。違反は `violation` として `decide()` に渡る。
