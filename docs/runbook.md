# Runbook — taskrail が期待どおりに動かないとき

最初に `taskrail doctor` を実行してください。設定の不備の大半はこれで分かります。

## ラベルを変えてもエージェントが起動しない

1. Actions の `taskrail` ワークフローの実行履歴を見る。実行自体がなければ、イベントが届いていません。
   - ラベルを付けたのが `GITHUB_TOKEN` だと、次のワークフローは起動しません。App のトークンで付ける必要があります。
2. 実行はあるが `route` がスキップしている場合、ログの `スキップ:` の理由を読む。
   よくある理由: `blocked` が付いている、`ai::ok` がない、キルスイッチ、操作した人に write 権限がない。
3. `TASKRAIL_ENABLED` が `false` になっていないか確認する。

## エージェントが途中で止まった・タイムアウトした

状態は Issue にあるので、やり直せます。Issue の最後の taskrail コメントを確認し、
`blocked` が付いていれば外して、同じ `flow::` ラベルを付け直してください。その工程が最初から走ります。

## 同じ Issue で差し戻しが続く

仕様が曖昧な可能性が高いです。ラベルを `flow::spec` に戻し、受け入れ条件を書き直してください。
仕様を見直すと、差し戻しの回数はリセットされます。

## 「保護対象のファイルが変更されました」で止まる

AIが設定の `protected_paths` に該当するファイルに触れました。作業ブランチは push されていません。
その変更が本当に必要なら、人間が行うか、Issue を分割して `ai::no` にします。

## 意図しない変更が大量に出た

1. リポジトリ変数 `TASKRAIL_ENABLED` を `false` にして全体を止める。
2. 該当の PR を閉じ、ブランチを削除する。
3. 原因を特定する(Issue の書き方か、プロンプトか、ルールの不足か)。
4. プロンプトが原因なら taskrail 本体へ、ルールが原因なら導入先リポジトリの linter・テスト・ルール文書へ反映する。
5. `TASKRAIL_ENABLED` を戻す。

## コストが想定を超えた

`taskrail metrics` と Actions の実行時間から、ターン数の多い Issue を特定します。
多くの場合、1つの Issue が大きすぎます。`size::l` を Plan 列で分割する運用を徹底してください。
