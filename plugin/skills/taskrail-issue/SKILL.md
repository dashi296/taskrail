# taskrail 向けの Issue を書く

AIの成果の質は、ほぼ Issue の質で決まります。あなたの仕事は、利用者の頭の中にある前提を引き出して文章にすることです。

## 手順

1. **依頼を理解する。** 関連するコードを読み、現在の振る舞いを把握する。

2. **足りない情報を聞く。** 特に次の点は推測で埋めない。
   - なぜ必要か(背景が分かると、実装者は細部を正しく判断できる)
   - 完了したと言える条件
   - やらないこと

3. **受け入れ条件を書く。** 1条件1事実で、テストか手順で確認できる形にする。
   - 悪い例: 「エラーを適切に処理する」「パフォーマンスを改善する」
   - 良い例: 「APIが500を返したとき『保存に失敗しました』と表示し、入力内容は保持される」
   - 「適切に」「正しく」「必要に応じて」が出てきたら、具体的な振る舞いに置き換える。

4. **規模を見積もる。** 1つの PR が半日で終わらないなら、分割を提案する。
   依存関係は本文に `Depends on #12` の形で書く(着手の判断に使われる)。

5. **AI に任せてよいかを判断する。** 認証・認可、課金、マイグレーション、インフラ、CI 定義に触れるなら、
   `ai::no` を提案する。

6. **下書きを利用者に見せてから起票する。**
   `gh issue create --template task.yml` は対話的なので、本文を組み立てて
   `gh issue create --title "..." --body-file <file>` を使う。ラベルは付けない(起票すると自動で `flow::inbox` に載る)。

## 本文の構成

Issue テンプレート(`.github/ISSUE_TEMPLATE/task.yml`)と同じ見出しを使う:
背景 / 目的と期待する結果 / 受け入れ条件 / スコープ外 / 触ってよい範囲 / 参考情報と依存
