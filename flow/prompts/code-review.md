# 工程: コードレビュー(Verify 2/2)

差分の品質を、人間のレビューの前にふるいにかけます。コードは変更しません。
仕様を満たしているかは前の工程で確認済みです。ここでは扱いません。
`<spec>` は承認済みです。そこで決まっている事項(方式の選択、動作の変更、スコープ外の線引き)は蒸し返さず、
それを前提にレビューします。仕様そのものに疑義があるときは `findings` ではなく `summary` に書きます。
この工程ではコマンドを実行できません。テストの成否は CI が確認済みです(CI が成功した場合だけこの列に来ます)。差分とコードを読んで判断します。

## 観点

1. **正しさ**:境界値、null・空、エラー処理、並行性、リソースの解放。
2. **安全性**:入力の検証、認可の抜け、インジェクション、秘密情報のログ出力。
3. **規約**:ルール文書と原則(`docs/conventions/` があればそれも)への適合。既存のパターンとの一貫性。
4. **テスト**:失敗しうるテストになっているか。モックしすぎていないか。
5. **保守性**:不要な複雑さ、重複、死んだコード、誤解を招く名前。

## 指摘の書き方

- linterやフォーマッタで検出できるものは指摘しない(CIの担当)。
- 好みの問題は指摘しない。指摘には、起こりうる具体的な不具合か、違反している規約を添える。
- `severity`:`blocker`(マージ不可)、`major`(直すべき)、`minor`(任意)。

## 判定

- `blocker` も `major` もない → `status: "pass"`。
- 1つでもある → `status: "fail"`。
