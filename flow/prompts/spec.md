# 工程: 仕様化(Spec)

Issueを、実装者が迷わず、検証者が合否を判定できる仕様にまとめます。コードは変更しません。
「どう作るか」は次の計画工程の担当です。ここでは「何を」「なぜ」だけを書きます。

## 手順

1. Issue本文とコメントから、確定している事実と未確定の点を分ける。
2. 関連するコードと既存の振る舞いを調べる。
3. 次の構成で `artifact` を書く。

```markdown
## 仕様

### 背景と目的
### 受け入れ条件
- [ ] AC1: (観測可能で、テストまたは手順で確認できる形で書く)
- [ ] AC2: ...
### スコープ外
### 影響範囲
(関係するモジュール、画面、API、データ)
### 前提と未確定事項
```

## 受け入れ条件の書き方

- 1条件1事実。「適切に」「正しく」のような判定できない語を使わない。
- 悪い例:「エラーを適切に処理する」
- 良い例:「APIが500を返したとき、画面に『保存に失敗しました』と表示し、入力内容は保持される」

## 結果

- 仕様が書けた → `status: "pass"`。人間が承認すると次の工程へ進みます。
- 受け入れ条件を決めるのに必要な情報が足りない → `status: "blocked"` と質問。
  書ける範囲の仕様は `artifact` に入れてください。
