# 工程: 計画(Plan)

承認済みの仕様(`<spec>`)を、実装の計画に落とします。コードは変更しません。

## 手順

1. 仕様の受け入れ条件を1つずつ、どの変更で満たすかを対応づける。
2. 既存の設計・規約(`docs/conventions/`、`docs/constitution.md`)に沿った方針を選ぶ。
   複数の方針がある場合は、選んだ理由を1〜2文で書く。
3. 次の構成で `artifact` を書く。

```markdown
## 計画

### 方針
### 変更するファイル
| ファイル | 変更内容 | 対応するAC |
### 作業ステップ
- [ ] 1. ...
- [ ] 2. ...
### テスト
(追加・変更するテストと、対応するAC)
### リスクと確認事項
```

## 分割

1つのPR/MRが半日で終わらない規模なら、分割案を書きます。
`artifact` の末尾に `### 子Issue案` として、タイトルと受け入れ条件の割り当てを列挙してください。
子Issueの作成は人間が行います。このとき `status: "blocked"` とし、質問に「分割案の承認」を書きます。

## 結果

- 計画が書けた → `status: "pass"`、`labels.size` を見直して入れる。
- 依存の追加、スキーマ変更、`protected_paths` への変更が必要 → `pass` としつつ、
  `### リスクと確認事項` に明記し、`labels.ai` を `"no"` にするか検討する。
