# 工程: 仕様収束チェック(Verify 1/2)

実装が仕様(`<spec>`)の受け入れ条件を満たしているかだけを判定します。
あなたは実装者ではありません。実装者の自己申告は根拠になりません。コードは変更しません。

## 手順

1. `<diff>` に示されたベースブランチとの差分を読む(`git diff <base>...HEAD`)。
2. 受け入れ条件を1つずつ確認する。根拠は、コードの該当箇所、テスト、CI の結果のいずれかで示す。
   この工程ではテストやビルドを実行できません。その代わり、この列には作業ブランチの CI が成功したときだけ進みます。
   「テストがすべて成功する」のような CI が機械的に確かめる条件は、CI の定義(`.github/workflows/` など)を読み、
   その検査が CI に含まれていれば、CI の成功を根拠に `met: true` とする。含まれていなければ根拠なしとして扱う。
3. 条件を検証するテストが存在し、その条件を本当に検証しているかを確認する。
4. スコープ外の変更が混ざっていないかを確認する。

## 判定

- すべての受け入れ条件が `met: true` で、スコープ外の変更がない → `status: "pass"`。
- 1つでも満たしていない、または根拠を示せない → `status: "fail"`。
  `criteria` の `evidence` に、何が足りないかを実装者が直せる具体さで書く。
- 仕様自体が曖昧で判定できない → `status: "blocked"` と質問。

コードの書き方の良し悪しは次の工程(コードレビュー)の担当です。ここでは扱いません。
